# 引き継ぎからの再開

現在の依頼と引き継ぎから未完了の作業を確認し、関連する変化を確かめたうえで、許可された次の作業を実行する。
読み込みやタスクリスト作成だけで、再開の依頼を完了扱いにしない。

## 現状と引き継ぎを照合する

指定された文書を読む。省略された場合はプロジェクトが定めた記録先を優先し、指定がなければリポジトリ直下（Git がない場所では cwd）の STATE.md、HANDOFF.md、既知の docs 配下の順に候補を探す。
STATE.md がある場合は現在の作業状態をそこから確認し、再開に必要な詳細は関連する HANDOFF.md や参照先から読む。HANDOFF.md だけの既存作業も再開できる。
広い履歴検索は必要なときだけ行い、複数候補から目的を特定できない場合は確認する。
特定の見出し名や生成ツールを必須にせず、目的、完了済み、未完了、失敗した方法、承認と制約を読み取る。

記録された commit・branch・対象ファイル・必要な外部状態と現状を比較する。
Git のある場所では status、関連 diff、記録以降の log を確認し、Git がない場所ではファイルを直接照合する。
文書の古さだけで期限切れと判定しない。外部状態は作業上必要なら現在の証拠を取る。

## 差分をどう扱うか

- 無関係な追加や完了済み作業: 状態を更新して説明し、既存変更を保全して先へ進む。
- 依頼に沿う関連変更: 引き継ぎの手順を現在の実装・仕様に合わせる。
- 目的・仕様・権限・対象の同一性を変える衝突: 依存する変更を止め、決定が必要な点を確認する。独立した許可済み作業は進めてよい。
- 危険な古いコマンドや現行規則との矛盾: 現在の指示を優先し、何が古く何を採用したかを示す。

drift があるという理由だけで、取得済みの許可を聞き直さない。未実行の検証を成功扱いせず、過去の失敗を無条件に繰り返さない。

## 作業と完了

目的、再開位置、判断を変える drift を短く伝えて実行する。
複数の作業がある場合は利用可能なタスク管理手段を使う。特定のツールがないという理由だけで再開を止めない。
受入条件に対応する検証まで実行し、結果・残る未完了・必要な判断を報告する。

作業状態の保存先・更新時点・HANDOFF.md の整理は、現在の依頼とプロジェクトの方針に従う。指定がなければ次を使う。

- STATE.md に目標、現在地、未完了事項、障害、次の一手、最終確認時点と根拠への参照を短く残す。検証済み・未検証・承認待ちを区別する。
- 重要な進捗・判断・障害の変化後と、中断・終了前に更新する。HANDOFF.md だけで再開した場合も、継続作業の状態は STATE.md にまとめる。
- HANDOFF.md は、STATE.md だけでは再開に足りない詳細がある場合に使う。同じ情報を両方で管理しない。
- 対象作業の完了を検証し、後でも必要な判断・知見・検証結果を適切な記録先へ残してから STATE.md を更新し、当該 HANDOFF.md を直ちに取り除く。削除・退避方法はプロジェクトの方針に従う。他の未完了作業を含むファイルは丸ごと消さない。
- 完了履歴を STATE.md に積み上げず、進行中の作業がなければその旨を明記する。他の作業状態や過去の記録を勝手に上書きしない。

文書に残された承認は現在の依頼と適用範囲を照合する。memory の更新は利用可能な更新口と明示された許可に従う。
