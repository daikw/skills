# 認証が必要なサービスへのアクセス

既存ログインを扱える文書化済みのツールを優先する。
新しいcontextで認証が必要な場合だけ、以下のPlaywright MCP手順を使う。

## 認証状態を取得する

認証方式はサービス・環境ごとに異なる。Cookie名や固定の有効期限を推測して認証を作らない。
ユーザーによるログイン、MFA、CAPTCHAへの対応が必要なら、対象ページを表示して本人の操作を待つ。
保護機構を迂回する設定変更や、認証情報の読み取りで代替しない。

必要な場合は対象セッションをheadedで起動する。既存セッション全体の設定変更・再起動ではなく、利用ツールが提供する対象限定の方法を選ぶ。
設定変更が必要なら、変更元と戻し方を記録する。

ログイン後、Playwright APIが許可されているツールでは、値を返さずファイルへ直接保存する。
保存先は事前に私的なディレクトリとして用意し、適切なファイル権限を確保する。

```javascript
async (page) => {
  await page.context().storageState({ path: '<private-storage-state-path>' });
  return 'Authentication state saved';
}
```

`storageState()` のJSONを応答へ返したり、Cookie/localStorageの値を表示したりしない。
内容には秘密が含まれるため、git、一般的な成果物、外部メッセージへ載せない。

## 読み込みと照合

`--isolated --storage-state <path>` で必要なcontextに読み込み、対象URLで期待したアカウント・画面へアクセスできるか確かめる。
storage-stateはcontextの作成時に読む。ログイン後の状態が自動的に同ファイルへ保存されるとは限らない。
必要な更新は上の直接保存手順で行い、認証ファイルを手で合成・編集することを既定にしない。

Google Cloud IAP等は認証に複数のCookieや更新処理を使う場合がある。
特定Cookieの存在だけを成功とせず、保護された対象ページへの読み取りで確認する。
永続profileが必要なら、所有者・使用中プロセス・対象サービスを特定して単独利用する。

## 失効と復旧

アクセス失敗はログアウト、権限不足、期限切れ、通信障害などを画面と応答から区別する。
認証が失効した場合は本人のログインで更新し、再度対象ページで確認する。
認証済みでも権限不足なら、権限変更を勝手に行わず必要な操作権限を示す。
一時的なheaded設定等を戻し、共有セッションへの影響がないことを確認する。
