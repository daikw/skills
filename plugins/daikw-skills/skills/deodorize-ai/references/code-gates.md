# Code gates — コードゲート（C 系）

code ルートのゲート。4 tier 構成: surface（C-S）→ defensive（C-D）→ structural（C-T）→ test（C-X）。表層を潰しても構造は残るので、tier を独立に評価する。捏造系（幻の import・幻の統合）は universal F-4 の具体形としてここに置く。

**このルートでは反復は規約適合の証拠。** 既存コードと同じ形式・命名・構成であることを flag しない。逆に「リポジトリに前例がない様式の持ち込み」が tell になる。

**誤検出ガード**: 各 tell には「存在するが正当」なケースがある（理由が文書化された fallback、信頼境界での防御、移行期間の `_v2`、CI で意味を持つ絵文字ログ等）。既存コードに一貫した前例があればプロジェクトの様式であって slop ではない。

## C-S 系: surface（コメント・命名・残骸）

### C-S1 実況コメント — minor（密度が高いと最強の識別子）

- 検出: コメントを削除して情報が 1 ビットでも失われるか？ → No なら陽性。コードの what を言い直しているだけ。
- grep: `//\s*(Import|Initialize|Set|Get|Return|Loop through|Create|Define|Call)\s`
- 修正: 削除。why（意図・制約・トレードオフ）を語るコメントだけ残す。

### C-S2 Step 連番コメント — minor

- 検出: 1 関数内に `Step 1:` / `1.` 形式の連番コメントが 2 個以上連続するか？
- 修正: 削除。手順に意味があるならフェーズごとに関数を切る。

### C-S3 コメント・ログの絵文字 — major

- 検出: コメント・ログ・print に絵文字があり、かつリポジトリに前例がないか？（両方 yes で陽性）
- なぜ: chat UI 向け装飾癖の漏出。レビュアー証言「コメントに絵文字があれば確定」。
- 反証: 絵文字ログには正当な用途がある（ANSI が剥がれる CI での可読性）。前例があれば様式。
- 修正: 規約に合わせる。前例がなければ削除。

### C-S4 自信のないコメント — major

- 検出: `should work` / `hopefully` / `may need adjustment` / 「たぶん動く」があるか？
- なぜ: 未検証コードが混入している自己申告。
- 修正: 検証して断定するか、TODO + tracking issue に格下げする。

### C-S5 制作過程への言及 — major

- 検出: `Here's the implementation` / `Generated by` / `As requested` / 「実装フェーズ」等、成果物ではなく制作過程に言及するコメントがあるか？
- 修正: 全削除。

### C-S6 debug 残骸 — major

- 検出: 本番パスに `console.log` / `print()` / `std::cout` が残っているか？
- 修正: 削除、または既存ロガーに置換。

### C-S7 汎用命名 — minor

- 検出: `data2` / `result` / `temp` / `helper_1` のような、何を持つか示さない識別子があるか？
- 修正: ドメイン語で命名し直す。

### C-S8 他言語イディオムの混入 — critical

- 検出: そのファイルの言語に存在しないメソッド・イディオムが使われているか？（Python に `.push()` / `.length`）
- なぜ: 多言語混合の訓練分布で他言語の最頻形に滑る。多くの場合そもそも動かない。
- 修正: 目標言語のイディオムに直す。

## C-D 系: defensive（防御過剰・バグの沈黙化）

### C-D1 例外の握り潰し — critical

- 検出: catch/except の中身が「空」「ログのみ」「デフォルト値返しのみ」か？
- grep: `except[^:]*:\s*(pass|return (None|""|\[\]|\{\}))` / `catch\s*\([^)]*\)\s*\{\s*\}`
- なぜ: モデルは不変条件を知らないので防御が安全な既定値になる。クラッシュをサイレントなデータ破損に変換する。
- 修正: 具体的な例外型のみ catch。処理できない失敗は伝播させる。

### C-D2 欠損を隠すフォールバック — critical

- 検出: `|| {}` / `.get(..., {})` 連鎖が、入力の欠損や上流の失敗を呼び出し側から見えなくしているか？
- 修正: 欠損を検出して明示的に扱う。既定値は境界でのみ与える。

### C-D3 型システムからの逃亡 — major

- 検出: `as any` / `as unknown as` / `@ts-ignore` / bare `# type: ignore` で型エラーを抑止しているか？
- 修正: 実際の型を書く。境界の未知データは parse/validate する。

### C-D4 setTimeout 絆創膏 — critical

- 検出: 競合状態・初期化順序の問題に根拠のない固定 delay を挿入しているか？
- 修正: 真の同期プリミティブ（await・イベント・ready シグナル）に置換。

### C-D5 言語別 panic パターン — major

- 検出: テスト外の `.unwrap()`（Rust）/ ライブラリコードの `panic()`（Go）/ `async void`（C#）/ mutable default 引数（Python）があるか？
- 修正: 各言語のエラー伝播機構に置換。

### C-D6 セキュリティ境界の手抜き — critical

- 検出: SQL の文字列連結 / シェルへの未検証入力 / `innerHTML` への未サニタイズ値 / 認証だけあって認可チェックがないルート、があるか？
- 修正: パラメータ化クエリ、引数配列 exec、サニタイズ、認証と認可の分離。

### C-D7 ハードコードされた環境値 — critical（秘密情報）/ major（URL・ID）

- 検出: 本番コードに環境固有 URL・ID・認証情報の直書きがあるか？
- 修正: 環境変数・秘密管理へ。**コミット済みの秘密はローテートする。**

## C-T 系: structural（骨格・重複・投機）

### C-T1 同義ヘルパの増殖 — major

- 検出: `formatCurrency` / `formatMoney` / `displayPrice` のような同義ユーティリティが複数あるか？
- なぜ: モデルはコードベースの持続的モデルを持たず、先行実装を検索する動機がない。実測: 5 行以上の重複ブロックは 2024 年に 8 倍増（GitClear、211M 行）。
- 修正: 1 本に集約し全呼び出し元を通す。

### C-T2 `_v2` / `_new` クローン — major

- 検出: `foo` と `foo_v2`（`_new` / `_impl` / `_improved`）が同居し、旧実装に呼び出し元が残っているか？
- 修正: マージして真実の源を 1 つに。移行期間の共存は理由をコメントに残す（それは正当）。

### C-T3 単一実装の抽象化 — major

- 検出: そのインターフェース／ファクトリの実装は 2 つ以上あるか？ → 1 つなら陽性。
- 修正: インライン化して抽象化層を消す。→ 詳細レビューは `reviewing-overengineering` に委譲。

### C-T4 thin wrapper / 死んだ将来対応 / 1 箇所しか読まれない設定 — minor〜major

- 検出: 同じ引数で別関数を 1 回呼ぶだけの関数 / 呼び出し元のない「拡張性のための」コード / 参照箇所が 1 つのフラグ、があるか？
- 修正: インライン化・削除・ローカル化。→ `reviewing-overengineering` に委譲。

### C-T5 標準ライブラリの再発明 — major

- 検出: 手書き groupby / JSON 経由 deep copy / 手動 URL パース / 手書き日付計算があり、標準に等価物があるか？
- 修正: 標準機能に置換。

### C-T6 幻の import — critical

- 検出: import されたパッケージが manifest に存在するか？ レジストリに実在するか？ 使用メソッドがインストール済みバージョンに存在するか？
- なぜ: モデルは妥当性と実在性を区別しない。**typosquatting のサプライチェーン攻撃面でもある。**
- 修正: 実在確認 → lockfile 固定。supply-chain rules に従う。

### C-T7 動くように見える空実装 — critical

- 検出: 関数本体が `pass` / `...` / `return None` / 定数返しのみで、docstring はその関数が何かをすると主張しているか？（両方 yes = ドキュメントが嘘をついている）
- 修正: 実装するか、タスクを未完了として報告する。

### C-T8 "Almost right" ロジック — critical（静的検出不能）

- 検出: 空入力・単一要素・境界値・タイムゾーン跨ぎ・並行書き込みで壊れるか？ ページネーションが最終ページを落とさないか？
- なぜ: モデルは「正しいコード」ではなく「正しく見えるコード」を生成する。**このカタログで唯一 grep が原理的に効かない tell。** 境界は人間が手でトレースする。
- 修正: 境界に的を絞ったテスト、property-based test。

## C-X 系: test slop

### C-X1 モックを検証するテスト — critical

- 検出: 全協力オブジェクトをモックしており、実装のバグで落ち**えない**テストか？
- 修正: 外部依存だけモックし、振る舞いを検証する。

### C-X2 トートロジーテスト — critical

- 検出: `assert True` / 固定リテラル同士の比較があるか？
- 修正: 実装のバグで落ちる assertion に書き換える。

### C-X3 テスト改変による解決 — critical

- 検出: 修正 PR で失敗テストの**期待値側**だけが変更され、実装が変わっていないか？
- 修正: 実装を直す。テスト変更が正当な場合はその理由をコミットメッセージに残す。

### C-X4 assertion 品質 — minor〜major

- 検出: エラーメッセージのない assert の羅列 / 説明のない数値リテラル直書き / 対象メソッドを呼んでいないテスト、があるか？
- 実測: LLM 生成テストの 31% が assertion なし、37% が対象メソッドを呼んでいない（Codex ベースライン）。
