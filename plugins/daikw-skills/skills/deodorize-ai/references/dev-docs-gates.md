# Dev docs gates — README・技術文書（D 系）/ コミット・PR（P 系）/ 図（G 系）

dev-docs ルートのゲート。捏造・残骸は [universal-gates.md](universal-gates.md) を併用する。**このルートでは Markdown・箇条書き・表・定型フォーマットはそれ自体 tell ではない**（媒体の規約が正）。過剰・空虚・嘘だけを検出する。

## D 系: README・技術文書

### D-1 絵文字見出し — minor

- 検出: 見出し・箇条書きの先頭に 🚀 ✨ ✅ 💡 が体系的に付いており、リポジトリの他文書に前例がないか？
- 修正: 削除。ただしプロジェクトが一貫して使っているならそれはプロジェクトの声。

### D-2 README 骨格の既製品化（Template stamping） — major（構造 tell）

- 検出: README が「タイトル+バッジ列 → 説明 → 目次 → Features → Tech Stack → Installation → Usage → Roadmap → Contributing → License → Acknowledgements」の骨格をほぼそのまま持ち、プロジェクト固有の情報がない節（空の Roadmap・一般論だけの Contributing）があるか？ 複数文書が同一骨格か？
- なぜ: 訓練分布の README 最頻骨格の再生。**コードドメインで最も純粋な構造 tell。**
- 修正: そのプロジェクトが実際に説明すべきことから構成を決め、空セクションを消す。目次は見出し 10 個未満なら不要。

### D-3 バッジ・装飾のインフレ — minor

- 検出: 状態を反映しない装飾バッジ（言語アイコンの羅列）が並んでいるか？
- 修正: 状態を表すバッジ（CI・version・license）だけ残す。

### D-4 関数名から書かれたドキュメント — critical

- 検出: 説明が識別子名を敷衍しただけで、記述された挙動を実装が持っているか未確認か？ 実装と乖離した説明・存在しないクラスへの参照があるか？
- なぜ: 文法的に完璧な docstring は名前だけから生成できる。誤った説明はないより悪い。
- 修正: 実装を読んで書き直す。書けない箇所は削除する。universal F-4 と併走。

### D-5 宣伝文体の技術文書 — major

- 検出: `groundbreaking` / `seamless` / `robust` / 「画期的な」「シームレスな」「強力な」が技術文書に出るか？
- 修正: 形容詞を削除し、測定可能な事実に置き換える。

### D-6 箇条書き・太字の過剰 — major

- 検出: 因果・時系列でつながる論証が箇条書きに分解されているか？ 項目 2 つだけの箇条書き / 2 列 3 行程度の対比の表化 / 段落あたり複数の太字、があるか？
- 修正: 論証は散文に戻す。箇条書きは真の列挙にだけ使う。

## P 系: コミットメッセージ・PR・Issue

AI エージェント PR の実証研究（arXiv:2601.04886）があり、定量的裏付けを持つ唯一の領域。**diff が正、説明は従。**

### P-1 幻のコミット（Phantom Changes） — critical

- 検出: PR・コミットの説明が主張する変更のうち、diff に存在しないものがあるか？
- 実測: AI エージェント PR の不整合の 45.4% がこのカテゴリ。
- 修正: 説明を diff から再生成する。レビューは diff を正とする。

### P-2 スコープの過少申告 — critical

- 検出: diff に含まれる重要な変更が説明に書かれていないか？
- 実測: 不整合の 22.0%。レビュアーが変更を見落とす直接原因。
- 修正: 変更ファイル一覧と説明を突き合わせる。

### P-3 ボイラープレート説明 — major

- 検出: PR 本文がどの PR にも当てはまる一般論（「品質を改善しました」「保守性を向上させます」）だけで、この変更に固有の情報がないか？
- 修正: 「なぜこの変更が必要か」を 1 文で書く。書けないなら PR を分割する。

### P-4 attribution トレーラーの置き去り — major

- 検出: `Generated with ...` / `Co-Authored-By: <AI ツール>` トレーラーが残っているか？
- なぜ: ハーネスの既定値。「提出物をトレーラーに気づくほども読んでいない」証拠として解釈される。
- 修正: ハーネス設定で無効化する。

### P-5 完璧に整形された壁 — major（F-4 と共起で critical）

- 検出: 初回投稿の Issue・バグ報告が、完璧な英語・大量の箇条書き・整った節構成を持つか？
- なぜ: **整いすぎが逆に低品質のシグナル**という反転した判定基準（curl の観察: 質の低い人間の報告は数行、AI slop は整形された壁で届く）。
- 修正: 再現手順・観測された挙動・期待される挙動の 3 点に絞る。

### P-6 過剰実装 + ハッピーパステスト — critical

- 検出: PR が (a) 要求より広い解決策で、(b) テストがハッピーパスのみ、(c) 元 Issue のエッジケースを覆っていないか？
- 修正: Issue に書かれたケースをテスト名に 1:1 で対応させる。

## G 系: 図・ダイアグラム（Mermaid・アーキテクチャ図）

### G-1 情報量ゼロの箱と矢印 — critical

- 検出: 図が「API → Database → Queue」のような、そのドメインを知らなくても書ける汎用構成か？ ノード名が固有名詞ではなく一般名詞だけか？
- なぜ: 実システムの詳細構成は訓練データにないため汎用パターンに退行する。図は「理解した証拠」として流通するため、無情報の図は誤解を固定する。
- 修正: 全ノードを実在するサービス名・リポジトリ名に置換。置換できないノードは削除。

### G-2 幻のコンポーネント — critical

- 検出: 図中のコンポーネントに実在しないものがあるか？ 逆に実際の中核サービスが欠けていないか？
- 修正: ソースコード・IaC を正として全ノードを照合する。universal F-4 と併走。

### G-3 ラベルのない矢印 — major

- 検出: エッジにラベルがなく、何が流れるか（データ／制御／同期・非同期）不明なものがあるか？
- 修正: 全エッジにラベルを付ける。付けられないエッジは理解していない証拠なので、調べるか削除。

### G-4 グルーピング不在・過密 — major

- 検出: サブグラフ・境界（VPC・サービス境界）がなくノードが平坦に並んでいるか？ 1 図に 15〜20 コンポーネント超（Mermaid は 50 ノード超で可読性喪失）か？
- 修正: サブグラフで論理グループを明示し、階層図に分割する。

### G-5 装飾ノイズと画像化 — critical

- 検出: 図にグラデーション・ドロップシャドウ・装飾モチーフが付いているか？ 図がテキスト DSL でなくラスタ画像でコミットされているか？
- なぜ: 画像は diff が出ず、修正に全再生成が要り、grep できない。"almost right" 問題（誤りの修正コストが手作りより高い）。
- 修正: 図はテキスト DSL（Mermaid / PlantUML）で書き、装飾を削除する。
