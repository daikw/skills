# 実行契約

実行方法を変えても、実行者・編集者・評価者の情報境界を維持する。

## 実行前

- 対象の指示版、入力、fixture 初期状態、ハーネスとモデル、推論設定、ツールと権限を記録する。
- 評価者用の期待値・採点・失敗の仮説は実行者の読取範囲から外す。
- 正常ケースと判断境界を選び、何が観測されたら pass/fail/未実行/判定不能か決める。
- 金額・試行回数・停止期限が必要な実験では、利用者または実行環境の制約として決める。出典のない値を skill の標準にしない。

## 分離

変更可能な fixture と保護するファイルを区別する。異なる試行の成果物・session・cache・Git状態を混ぜない。
プロンプトで「ここだけ」と書くことと、OSやツールでアクセスを制限することは別の証拠である。
実行環境が分離を強制できない場合は、その限界を記録し、外部への実書込みを伴わないケースを選ぶ。
実機・GUI・共有DBなど単一のライブ状態を複数実行者に同時に触らせない。分離できない場合は直列化する。

## 起動と回収

使える subagent または fresh CLI を選ぶ。特定製品の Task/TodoWrite が必須とはしない。
既存 session を使い回すと前回結果が混ざるため、新しい実行者へ同じ入力を渡す。
モデルの役割や推論設定を勝手に変えない。起動不能は能力ゼロでなく NOT_RUN。

同期でも非同期でも、完了を示す結果と成果物を回収する。
非同期なら出力先、run ID、最終状態を対応付ける。idle、空出力、API health、受付成功だけでタスク完了としない。
タイムアウト時は既存実行が続いているか確認し、重複した実行を起動しない。

## 記録

保存するのは、必要な入力識別子、変更前後の指示識別子、許可された範囲、成果物、関連する実行記録、判定理由。
秘密・生の環境変数・認証ヘッダを出力や外部のレビューへ渡さない。
実測 metadata の無い metrics は取得できなかったと記載する。自己申告を使うならそう明記する。
数値でよく見えても必須条件の欠落・危険な副作用があれば失敗として扱う。

Codex CLI の具体的な起動方法が必要なら、同じ plugin の codex スキルを参照する。Claude など他のCLIも導入版の help で確認し、比較条件を固定して使う。
