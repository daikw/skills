# 指示を実行で検証する

指示を読んだ本人の感想だけで良否を決めない。
実行者が実際の依頼を完了できるか、必要な制約を守るか、不要な作業に誘導されないかを確認する。
文章量、実行者による妥当な方法選択を無くすこと、モデル名だけを成功条件にしない。

## 比較を成立させる

変更前に、解きたい失敗または不確実性と、維持すべき成果・境界を決める。
description と本文の用途が一致し、参照資料・script が実在することを確かめる。

典型的な依頼に加えて、変更した判断の境界が分かるケースを選ぶ。
例: 適用対象と似た対象外の依頼、許可済みの編集と未承認の外部操作、柔軟な分析と厳密なデータ変換。
入力、初期状態、モデル、推論設定、ツール、実行環境、変更する指示を記録してから比較する。
同じケースを比べ、難しさが違うケースのツール数だけで改善を主張しない。
実行者が読んだ実ファイル・版を、trace と正本/installed copy の照合で確認する。旧cacheを読んだ試行を改稿版の結果にしない。

評価者は、必要な成果、禁止される副作用、許容される裁量、観測方法をあらかじめ記録する。
必須条件は部分成功で埋め合わせない。実行前に評価基準を固定し、失敗を見てから都合よく緩めない。

未承認の外部操作を試験する場合は、実宛先へ届かない fixture・mock・適切な制限を使う。実書込みが起き得る環境ではその試験を起動しない。
指示を読んで止まった場合と、permission/hook に拒否された場合を分けて観測する。

## 実行者に渡すもの

新規セッション・独立 subagent・独立 CLI プロセスなど、改稿の理由を知らない実行者を使う。
通常の依頼、実行に必要な fixture、対象スキル、許可された操作と範囲を渡す。
正当なタスク要件は隠さない。一方、評価者の期待する答え、想定故障、採点の内訳、前回の出力や修正理由は渡さない。

実行方法・記録・分離の詳細が必要なら [実行契約](references/runner-contract.md)を読む。
渡す依頼と評価記録の形に迷う場合は [記録例](references/evaluation-record.md)を使う。

## 成果物と記録で評価する

- 成果物が要求された意味と形式を満たしているか。
- 必要な skill/reference を使えたか。無関係な資料・操作・確認を増やしていないか。
- 対象の取り違え、権限拡大、秘密出力、データ破壊、再実行の重複がないか。
- 必要な検証・完了確認を省いていないか。途中結果を成功扱いしていないか。
- 非変更対象が保たれているか。検証環境外の副作用をどう観測したか。

実行者の迷い・裁量・再試行の自己申告は原因を調べる補助にする。
観測された tool calls・所要時間・入力量などは補助指標として、同じケースの条件付き比較に用いる。
モデルの自己申告を実測に見せず、trace に無い指標は未取得とする。
Astra と Fable など複数対象は別々に記録し、一方の成功で他方を代替しない。

## 改善と停止

観測した失敗を、選択、参照構造、本文の判断、tool/script、環境、モデル/ハーネス固有差、評価者の誤りに分類する。
指示が原因ならその原因に対応する変更を行い、同じ条件の新しい実行者で確認する。
正しい裁量を固定手順で潰さず、機械的に命令・回数・subagent を追加しない。

既知の失敗を解消し、改稿や採点調整に使っていない入力の変種でも必要条件を保ち、残る不確実性が追加検証を要しなければ完了とする。
繰り返し数・ケース数・合格点・時間変動率に汎用の固定値を置かない。
結果が不安定なら、何を識別するために次の試験が必要かを述べて追加する。
利用者の費用・時間・操作制約で止まる場合は、改善済みと残る未知を分け、成功や収束を装わない。

独立実行が利用できない場合は、構造レビューと empirical 未実行を分ける。
自己再読を独立実行の代わりにせず、実行できる環境・権限・入力が何かを報告する。
