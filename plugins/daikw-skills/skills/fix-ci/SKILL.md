# Fix CI

失敗した実行と変更対象を特定し、根拠のある原因説明、または検証済みの修正を返す。

判断と固定条件: 原因調査と修正方法は状況に合わせる。対象の同一性、依頼の権限、修正後の検証は固定する。

## 対象と依頼

URL・会話・リポジトリのremoteから、GitHub/GitLab、PR/MR、run/pipeline、対象commitを結び付ける。
CLIがインストールされているだけで対象サービスを決めない。対象が複数あり結果が変わる場合に確認する。

- **「CIどう？」などの状況確認**: 現状を読み、失敗なら原因と次の対処を報告する。編集・push・再実行は始めない。
- **「直して」などの修正依頼**: 根拠を調べた後、許可された変更と関連検証を続ける。同じ修正について再承認を挟まない。
- merge、送信、権限変更、保護の緩和などは、元の依頼とリポジトリの承認規則に従う。CI修正の依頼だけをmerge許可にしない。

## 原因から修正へ

まず失敗jobのログと、そのjobを定義する設定・実行コードを読む。
現在のworking treeとは異なるcommitの失敗を、現在も再現する不具合として扱わない。
独立した失敗か、先行jobからの連鎖かを切り分ける。

| 観測 | 確かめるもの |
|---|---|
| 依存の解決やinstallで失敗 | manifestとlockfile、固定version、registryの応答、install方針 |
| test / lint / 型の失敗 | 対象commitのコード、再現条件、設定と実コマンド |
| 権限・認証で失敗 | 秘密値を表示しない設定の有無と権限の範囲 |
| runner / network / timeout | 実行環境の証拠、失敗箇所、再実行で判別できる仮説 |

修正は観測した原因に対応させる。テストを緩めたり、secretsを表示したり、install保護やbranch保護を外して通さない。
再実行は、許可されていて、コード変更なしに確認できる仮説がある場合に行う。

## 検証と完了

修正前の再現と修正後の確認はリポジトリのテスト方針に従う。
ローカル検証には既存のtask/script/インストール済みtoolを使い、コマンドを推測して外部コードを一時取得しない。

pushまで許可された作業では、pushしたcommitを対象にしたCI結果を照合する。古い緑のrunで完了にしない。
実行中・環境不足・アクセス不能ならその状態を示し、検証済みと書かない。

報告には対象run/pipelineとcommit、原因の証拠、変更、検証結果、未解決事項を含める。
調査依頼なら説明が揃えば完了。修正依頼なら変更した振る舞いの検証を終え、依頼されたCIの成否まで確認する。
具体的な取得コマンドは [references/ci-commands.md](references/ci-commands.md) を必要なサービスについて読む。
