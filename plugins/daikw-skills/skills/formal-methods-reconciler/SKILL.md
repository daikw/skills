# 仕様と実装を反例で照合する

確認したい主張を明文化し、機械で検証できる最小のモデルと、業務の言葉で読める結果を残す。
モデルが正しいかという問題と、モデル内で性質が成立するかという問題を分ける。

## 先に確認すること

- 対象の仕様、コード、設定、テスト、観測ログとその版を特定する。実装の現状を望ましい仕様と同一視しない。
- 許される入力・操作、禁止状態、到達可能性、最終的に成立すべき性質を、根拠と対応付ける。
- 欠損、エラー、再送、タイムアウト、クラッシュが主張を変える場合はモデルに含める。
- 仕様同士の矛盾や未定義の方針は、反例で具体化して決定者へ返す。実装に合わせて仕様を無断で決めない。

通常のテストや条件表で判断できるなら、それを使う。形式手法を使うこと自体を成果にしない。

## 検証方法を選ぶ

既存のモデル、検証器、言語、CI を優先する。新しいツールの導入を調査の前提にしない。

| 確認する性質 | 候補 |
|---|---|
| 入力条件、設定の整合性、述語の同値性 | 有限領域の全列挙、SMT（Z3 など） |
| 権限、所有関係、テナント境界、グラフの制約 | Alloy などの関係モデル |
| 順序、再試行、クラッシュ、並行実行、活性 | TLA+ などの状態遷移モデル、P などのイベントモデル |
| 実装の事前・事後条件やループ不変条件 | 対象言語の検証器、Dafny、Verus、CBMC など |
| 帰納的な数学上の主張 | 既存の証明基盤（Lean、Rocq など） |

これは候補の対応表であり、特定ツールだけが扱えるという制限ではない。
選んだツールの仕様と実行方法は、インストール済みの版と公式資料で確認する。
必要な検証器が無ければ、モデル・実行計画・手計算の反例まで進め、機械検証済みとは書かない。

## モデルと結果

- 主張に必要な入力、状態、操作、制約に絞り、コードからモデルへ省略・抽象化したものを記録する。
- 有効な入力や到達可能な成功経路も確認する。前提が矛盾して全入力を排除した「成功」を防ぐ。
- 性質に違反する既知の例や変種が検出されるか、可能な範囲で確認する。実システムを故意に壊して検証しない。
- 反例を消すために不変条件や前提を弱めない。モデルの誤りと製品の誤りを切り分ける。
- SAT/UNSAT だけでは結論にならない。何を問い合わせたか、反例の入力・操作順・状態を残し、誰が何をできてしまうか説明する。
- 探索の上限、対象領域、公平性などの仮定、タイムアウト、未検証の接続部分を明記する。有限範囲の検証を一般的な証明に拡大しない。

## 既存モデルを更新する場合

変更前の主張、モデル、期待結果、検証器の版と、現在の仕様・コードの差分を照合する。
失敗原因を仕様変更、実装変更、モデルの陳腐化、検証環境の違いに分ける。
既存の反例と確定済みの業務判断を保存し、実際に影響する性質を再確認する。
期待結果の更新や CI 化は依頼範囲で行い、承認されていない仕様変更・投稿・デプロイへ進めない。

## 成果物

主張と出典、モデルの範囲、実行コマンド・環境・実測結果、反例または成立した性質、未決の仕様判断を残す。
依頼が計画だけなら計画で完了してよい。実行を依頼されたのに実行できなければ、未完了の検証を明示する。
