# コードと業務用語の対応を残す

読者が用語の意味、実装の所在、次に読む資料をたどれる文書を作る。
対象と出力先は依頼・現在の repo から特定する。用語集の依頼を全社構成の調査へ広げない。

## 調べる範囲

対象 repo、branch/commit、未コミット差分の有無を確認する。
複数 repo や組織全体が対象なら、読めた repo と未取得の範囲を区別する。
README、docs、schema、API、エントリポイント、IaC のうち用語と責務を説明するものを優先する。
名前の一覧から始め、関係する本文へ絞る。認証設定、環境変数、秘密ファイルを情報源として丸ごと読まない。

## 用語の意味を確かめる

業界の一般語、製品内で意味が限定される業務語、組織内の略称・旧称、実装の識別子を分ける。
同じ綴りでも repo や境界によって意味が違う場合は、それぞれの文脈を示す。
各項目には、用語、意味、分類、実装や資料の所在、根拠、混同しやすい概念を必要な範囲で記す。
推測は推測と明示し、名前だけから業務上の権限や責務を断定しない。矛盾する定義は両方の出典を残す。

## 必要な成果物だけを作る

- 用語集だけの依頼なら、指定された文書内の表や項目で完結させる。
- オンボーディングや構成説明も求められた場合は、repo ごとの責務、入口、API・データの境界と読む順番を加える。
- 図が理解を助ける場合に、根拠のある関係を Mermaid で示す。構成上の依存と実際の通信を混同しない。
- HCL の宣言・参照を追う依存図が主目的なら `terraform-mermaid` を使う。
- ファイルの分割や図の数を固定しない。既存文書の構造に合わせ、無関係な部分を上書きしない。

## 根拠と共有範囲

共有文書では remote と commit から、読者がたどれる GitHub/GitLab 等の出典リンクを作る。
未コミットの情報は commit に存在するようにリンクせず、作業中の情報とその所在を明示する。
remote が無いローカル専用資料では repo 相対パスと対象版を使い、架空の公開 URL を作らない。
認証情報を含む remote URL は転記しない。私有 repo の情報は同じ閲覧範囲の文書に留める。
静的な設定を稼働中の状態と同一視せず、調査時点と未確認の関係を記す。

## 確認と完了

主要な定義と図の辺をソースに戻って照合し、リンク先と対象版を確認する。
描画した図は既存の renderer で確認する。使えない場合は表示未検証と明示する。
成果物、調査した範囲、重要な未定義・矛盾、次に読む資料を返す。
文書を作る依頼だけで、スキル登録、メモリ更新、組織への投稿や公開を行わない。
AI 用スキル化を明示された場合は `meta-rules` に従い、機微情報の有無を確認し、編集元と配布先を決める。
