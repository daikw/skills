# Agent 指示の設計と更新

スキルは、対象のモデルが一般知識から復元できない知識と、仕事の判断を変える条件を提供する。
成果物と守る境界を明確にし、方法の選択は必要な範囲で実行者に委ねる。

## 記述の精緻さを選ぶ

スキル全体に一つの自由度を付けず、判断・操作ごとに選ぶ。同じスキル内で併用してよい。

| 対象 | 記述するもの |
|---|---|
| 複数の方法が成立し、結果を確認して直せる仕事 | 目的、制約、判断基準、完了条件。調査順や思考手順は任せる |
| 推奨手順があるが入力・環境で変わる仕事 | 通常の方針、その理由、別手段に切り替える条件。選択を助ける例 |
| 順序・対象・引数を誤ると誤送信、データ損失、権限逸脱、重複実行になる操作 | 前提、対象の識別、入力形式、操作順、不変条件、停止・復旧条件、実行後の照合 |
| 固有の API、組織規則、モデルが推測できない仕様 | 正確な事実と出典。必要な操作で読む参照資料 |
| 同じ厳密な処理を繰り返す仕事 | 既存の検証済みスクリプト。入出力・副作用・失敗時の扱いを説明する |

「必ず」「禁止」と書く場合は、従わない場合にどのような問題が起きるか説明できること。
承認境界・秘密情報・データ保全・供給元の確認は、モデルの世代を理由に弱めない。
一方、調査・下書きまで危険操作と同じ固定手順にしない。既定値、推奨、例を義務から区別する。
必須条件は必要な操作に結び付け、後段の認可や入力を、独立した前段の読取・検証・下書きの開始条件にしない。
精緻さを上げるために、未提供のAPI引数・応答・状態値・再送保証を作らない。根拠がない詳細は未確定として、その確認前にどの操作を止めるかを示す。
未確定事項の一覧と、実行手順の条件を照合する。例えば再送保証を未確認と書きながら「未完了なら再送」と指示しない。保証が確認されるまでは、その再送分岐を止める。

精緻さに迷う場合、混在したワークフローを分ける場合、複数ハーネス・モデル向けに改稿する場合は
[判断基準と例](references/skill-authoring-best-practices.md)を読む。

## 編集元と配置を決める

最初に、実際の loader が読むファイルと、その編集元、生成先・配布先を特定する。
名前が同じでも編集元が同じとは限らない。cache や installed copy だけを編集して完了しない。
公開 source の通常編集でも、秘密・個人情報・実機や組織の識別情報を持ち込んでいないか確認する。

- Rules: 仕事全体に適用する規範。ドメイン固有の操作手順を常設しない。
- Skills: 特定の目的で必要になる知識・操作契約。
- Agents: 独立した仕事の実行役。参照資料を読むだけなら別 agent を必要にしない。
- 一回の作業記録や個別プロジェクトの事実: そのプロジェクトの docs や作業記録。

新規配置・移行・削除・複数ハーネスへの配布・モデル差の配置を決める場合は
[配置と配布](references/placement-and-distribution.md)を読む。
既存の配置と依頼から決まることは再質問せず、公開範囲や成果物を変える未確定の好みだけ確認する。
chezmoi 管理下の更新時は [source と生成先の同期](references/chezmoi-sync.md)にも従う。

## 入口と詳細を設計する

description は能力と適用場面を識別できる長さにする。広いキーワード列挙や「何でも使う」誘導を避け、
既存ユーザーが使う対象名・呼称は保持する。除外条件は誤発動しやすい境界を明らかにするときに加える。

本文には対象、成果、必須の境界、判断基準、必要な参照先を記す。
複数のモードや長い手順は、読む条件を付けて references に分ける。
短い単一目的のスキルはその場で完結させ、分割のためだけの router を作らない。
移した先の過剰な手順や矛盾も直す。単に古い本文を別ファイルに隠して済ませない。

既存の名前、supported frontmatter、invocation policy、機能、出典を維持する。
名前や呼出し方を変える必要がある場合は、利用箇所・移行先を確認して変更を説明する。

## 変更と検証

- 変更前に、現在の問題、望む判断、維持すべき条件、確かめるケースを対応させる。
- 変更が必要な description・本文・参照資料・生成先を一緒に更新する。無関係な dirty 差分を保全する。
- 読んだ meta-rules の親ディレクトリを基準に `scripts/lint.sh <skill-name-or-directory>` を実行する。名前は同じ plugin の skills 配下、パス指定は指定先の SKILL.md が対象になる。診断が別スキルへの参照を誤検出した場合は、実在する所有先を確認して記録する。
- スクリプトを変更した場合は、その動作の検証を行う。
  [スクリプト検証観点](references/agent-skill-testing-checklist.md)から実際の副作用と失敗条件に合うものを選ぶ。
- 新規・大幅な本文改稿では `empirical-prompt-tuning` で独立した実行者に現実のケースを実行させる。
  改稿理由や評価者の答えを実行者に教えず、成果物・呼出し・未変更対象を確認する。
- 依頼または配布方針で定めた対象ハーネス・モデルで確認する。他モデルの成功、ファイル一致、自己申告だけで代替しない。

発動しないなら description、読み過ぎるなら参照構造、判断を誤るなら本文、実行に失敗するなら
操作契約・ツール・環境を調べる。常に文章を強める、agent を増やす、再試行を増やす、という対処はしない。
必要なケースを満たし、残る懸念が追加の変更・検証を要しなければ完了とする。行数や試行回数を成功条件にしない。対象で実行できない検証は未検証として残し、改稿・適用済みと全対象の検証完了を区別する。
