# スキルスクリプトのテスト設計チェックリスト

スキルに含めるスクリプトのテスト観点。Claude Code / Codex などのハーネスを問わず、
変更した振る舞い・副作用・対象環境に該当する観点を選ぶ。
[meta-rules](../SKILL.md) の「変更と検証」節と、対象リポジトリの方針に従う。

move-project の開発と Codex (GPT-5.3) のレビューに由来する例を含む。
そのときのツール、層数、実データ、承認手順を全スキルの義務にはしない。
例示したツールの新規導入や、実環境への書込をこの文書だけで認可しない。

## 核心原則: ツール境界の引き方

> **実行結果と副作用はツールで観測し、事前に定めた条件に照らして判定する。**
> エージェントの予想や成功の自己申告を、観測の代わりにしない。

検証したいことと手段の候補:

| 検証したいこと | 理由 | 手段の候補 |
|---|---|---|
| 自作の例が見落とす入力 | 同じ前提で生成・評価すると盲点が残り得る | 仕様の境界例、匿名化した実例、既存の fuzz / property test |
| サポートする OS / 実装の差分 | 推論だけでは実環境での互換性を証明できない | 既存 CI の対象環境、実機での隔離検証 |
| 書込や権限変更などの副作用 | 成功メッセージに現れない変化がある | 内容・mtime・権限など対象に合う差分計測 |
| 出力と仕様の対応 | テストの期待値自体が誤っている場合がある | 既知の正解、不変条件、別実装との比較 |
| 失敗の再現性 | 原因と修正の対応を確かめるため | 入力・実行条件の保存、乱数を使う場合の seed 記録 |

---

## 1. 仕様と観測からテストデータを選ぶ

仕様に書かれていない入力形式や命名規則に依存する場合は、許可された範囲の実例を読み取りで確認する。
仕様・既存 fixture で受入条件を検証できる場合、実データの追加収集を必須にしない。
観測した形を再現する匿名化 fixture を使い、秘密や個人情報をテスト資産や外部モデルに持ち込まない。

```bash
# 例: Claude Code のプロジェクトキー命名規則を観察してからテスト設計
ls ~/.claude/projects/ | head -20
# → 発見: gitlab.example.com → gitlab-example-com（. も - に変換）
# → この発見がなければ FZ-01 のバグは見つからなかった
```

入力の形が多様なら、処理の分岐を変える特徴で fixture を分ける。
例えばパス変換ではドット・空白・記号・対象ファイルシステムの境界長が候補になる。
サンプル数や長さの閾値は対象仕様・観測・リポジトリ方針から選び、この例から固定値を作らない。

---

## 2. 変更に必要なテスト層を選ぶ

次は選択肢であり、一律に全層を新設するチェックではない。既存テストで証明できる条件は再利用する。
書込や部分失敗がある場合は、正常出力だけでなく、守るべき状態と失敗後の復旧を確認する。

| 層 | 対象 | 例 |
|---|---|---|
| **ユニット** | 純粋関数・変換処理 | `_escape_sed_pattern` 単体 |
| **統合** | スクリプト全体の入出力 | `migrate.sh src dst` |
| **副作用** | ファイルシステムへの影響 | mtime・permissions・バイナリ |
| **失敗注入** | ロールバック動作 | mv権限不足・途中中断 |

移動スクリプトなら、隔離した fixture に対して移動先の内容、元のパスの状態、対象外ファイルを照合する。
mtime や権限の保存が契約に含まれる場合は、それらも操作前後で測る。
失敗を表示するだけでなく、検証コマンド自体が失敗を終了コードに反映するようにする。

---

## 3. 入力と環境の境界例（シェルスクリプト向け）

対象が受け取る入力と、サポートする環境に絞る。広い自動生成が必要な場合に fuzzing を選ぶ。

```
入力の多様性:
□ セデリミタ文字を含むパス（| @ # など）
□ 正規表現特殊文字（. * [ ] ^ $）
□ スペース・タブを含むパス
□ ドット入りコンポーネント（domain.com → キー変換に影響）
□ 対象ファイルシステムの制限に近いパス・コンポーネント長
□ Unicode・日本語
□ src と dst がプレフィックス関係（/tmp/foo と /tmp/foo-new）

環境の多様性（Environment Fuzzing）:
□ locale, TZ, umask の差異
□ macOS(BSD) vs Linux(GNU) の sed/grep/stat 差分
□ mtime の粒度・clock skew
□ バイナリファイルが混在するディレクトリ
□ ファイルシステム種別（APFS, ext4, NFS）

既存・承認済みツールの候補:
- Radamsa: 入力の変異生成（出力は隔離した対象で検証する）
- ShellCheck: 静的解析（クォート・グロビング問題の早期検出）
- Bats / ShellSpec: 構造化テストフレームワーク
```

---

## 4.「動いた」と「正しく動いた」を区別する

終了コード 0 ≠ 正しく動いた。無言の失敗が最も危険。

元の move-project 開発記録には、BSD sed の正規表現処理が空出力になり、
後段の置換が誤動作した例がある。終了コードだけでなく、エスケープ関数が期待する文字列を返すか、
その出力を使う処理が誤った対象を書き換えないかを照合する。
エラーが呼出し元に伝わるかも、実際のスクリプトと対象環境で確認する。

**移動・変換スクリプトでの不変条件の例**（対象の契約に合うものを使う）:
- 「対象外ファイルは 1 バイトも変わらない」
- 「変換後のキーは全プロジェクトで一意」
- 「dst が存在する場合は src を移動しない」

---

## 5. 独立した根拠で盲点を調べる

自作テストは利用できる。ただし、期待値が実装と同じ誤解から作られていないか確認する。
仕様、実測、既存の回帰ケースなどに根拠を置き、重大な境界や未検証の前提には独立した確認を加える。
新規・大幅なスキル本文改稿は、主 SKILL.md の独立実行による検証に従う。
別モデルによる反証ケース作成は追加の手段であり、全スクリプトでの別モデル起動を要求しない。

```
追加検証の候補:
1. Seed Corpus（実データ匿名化）+ Mutation（SEED固定で再現可能）
2. Metamorphic testing: 入力が変わっても守る「関係」を先に定義
3. Cross-model-play: Claude が設計したテストを Codex/Gemini に壊させる
4. Environment fuzzing: locale/TZ/FS種別/umask をランダム変化させる
5. Oracle fuzzing: 判定器（テストハーネス）自体を壊しにいく
```

## 6. 実行の認可とテストの合否を分ける

過去のレビューでは、不変条件・危険な副作用の範囲・本番適用の判断が確認点として挙がった。
これは毎回三つの承認を取り直す義務ではない。

- 受入条件は依頼・既存仕様・リポジトリ方針から具体化する。成果が変わる未確定事項だけ確認する。
- 書込先、削除対象、権限変更、本番適用の認可は、適用されるルールと既存の明示的な許可を確認する。許可済みの範囲では重ねて承認を求めない。
- テスト合格を、未許可のデプロイ・送信・実機操作の許可に読み替えない。後段の認可が未取得でも、独立して行える読取・fixture 準備・検証は進める。
- 冪等性の検証は、実環境で危険な操作を繰り返す許可ではない。隔離した対象で証明できるかを先に判断する。

---

## 7. 見落とされがちな観点

1. **テストハーネス自体のバグ** — diff・終了コード解釈・grep のオプションが壊れているケース（過去の例: `grep -q "$VAR"` で変数が `-` 始まりだとオプション解釈された）

2. **ファイルシステム意味論** — mtime 粒度・rename 原子性・`sed -i` の実装差・NFS/overlayfs が本体バグを生む

3. **終了コード契約の曖昧さ** — stdout 一致だけ見て stderr/終了コード契約を見ないと「成功扱いの失敗」を量産する

---

## 8. ライブ外部環境を操作するスキルのテスト

GUI アプリ・実機・SaaS ダッシュボードなど、**巻き戻せる sandbox が存在しない外部環境**では、隔離・対象の識別・副作用の照合をテスト設計に含める。ファイルシステム用の fixture と同じ感覚で扱うと、テストの副作用が実環境に残り続ける。

実際に起きた事故: EasyEDA 操作スキルの empirical testing で、テスト実行のたびにユーザーのサンプルプロジェクト内へ匿名の `Board1`〜`Board8` が堆積し、並列実行では複数エージェントが同じ GUI ウィンドウを取り合って成果物が相互汚染した。

1. **認可されたテスト対象を識別する** — 専用プロジェクト・sandbox・複製を優先する。実データへの操作が必要なら、既存の許可がその対象と操作を含むか確認する。許可が足りない操作だけを止め、独立した準備は進める。

2. **テスト成果物に命名規約を課せ** — テストが作る資源には `test-<日付>-<目的>` のような識別可能なプレフィックスを付け、後から一括発見・クリーンアップできるようにする。`Board1` `Untitled` のような匿名リソースの堆積は環境そのものを汚す。

3. **1環境1エージェントを守れ** — GUI アプリ・実機・単一ウィンドウのような単一インスタンスのライブ環境に対する並列テストは禁止。直列化するか、環境インスタンス自体を分離する。

4. **クリーンアップ手順をテスト設計に含めよ** — 削除操作が破壊的で自動化すべきでない場合は、作成した資源の一覧（UUID・名前）をレポートに残し、人間が後で安全に消せるようにする。

5. **リセット不能な環境では代替検証を先に検討する** — 新規資源の追加にも副作用がある。追加・変更・削除の必要性、認可、保全・復旧方法を確認し、既存データを失う恐れが残る操作は実施しない。代替検証で確認できた範囲と、ライブでは未検証の範囲を区別する。

---

## 観測手段を選ぶ

標準コマンド・言語の標準ライブラリ・既存 CI / テスト基盤で受入条件を測れるかを先に確認する。
ShellCheck、Bats / ShellSpec、ファジングや OS 監視ツールは、必要な場合の候補であり導入必須ではない。
新規導入は対象リポジトリの依存・サプライチェーン方針に従い、実行可能性と権限を確認する。
監視ツールや環境固定ツールを採用しただけで、副作用の不在や OS 間の同一動作が証明されたとは扱わない。

## チェックリスト

```
テスト設計前:
□ 変更した振る舞い・受入条件・守る状態を対応させたか
□ 未知の入力形式に依存する場合、仕様や許可された観測で確かめたか
□ 対象 OS・ツール版・外部操作の認可範囲を確認したか

テスト設計中:
□ 必要な層を選び、既存の検証を再利用したか
□ 実際の入力境界・副作用・失敗条件をケースに含めたか
□ 終了コードだけでなくアウトカムを検証しているか
□ テストハーネス自体の正しさを確認したか

テスト実施後:
□ 実行した環境・結果・未検証範囲を記録したか
□ fixture と実入力の差が受入条件に影響する場合、その差を検証したか
□ 独立検証が必要な判断に、自己申告以外の根拠があるか
□ 作成した外部資源と残る副作用を照合したか（該当する場合）
```
