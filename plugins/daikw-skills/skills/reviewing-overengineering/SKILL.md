# 過剰設計レビュー

差分が持ち込んだ**不要な複雑さ**だけを探す read-only レビュー。
正しさ、セキュリティ、性能、可読性は扱わない。通常のコードレビューを済ませた後に走らせる補完的なパスである。

Freedom Level: **低** — 判定基準と証拠要件から逸脱しない。憶測で finding を出さない。

## 対象範囲

既定は**現在の差分**。リポジトリ全体の棚卸しは、ユーザーが明示的に求めたときだけ行う。

比較の基点（base commit / ブランチ / working tree）を最初に確定し、報告に明記する。
基点が確定できないまま finding を出さない。

## 判定基準

タグや重大度ラベルを発明しない。判定はこの一つだけで行う。

> **この要素を削除しても、依頼された要件を現在の入力と環境の下で証明できるか。**

証明できるなら finding にする。できないなら finding にしない。

次はいずれも finding の根拠にならない。

- 将来こう拡張されるかもしれない
- 一般にはこう書くのがベストプラクティスとされる
- 短く書ける
- 他の場所ではこうなっている

「理論的にはこの分岐が必要になりうる」も根拠にならない。
現在の入力と環境で観測できる必要性だけを見る。

## 発火の候補になる差分

以下を差分に見つけたら、削除判定にかける。見つけたこと自体は finding ではない。

- 新規の外部依存
- 実装が 1 つしかない interface / 抽象基底クラス / factory
- 呼び出し元が 1 箇所しかない設定項目・環境変数・フラグ
- 引数をそのまま渡すだけの wrapper 関数
- 標準ライブラリまたはプロジェクト内の既存ヘルパと同じことをする新規コード
- プラットフォーム標準の機能で置き換えられる自前実装
- 現在どこからも到達しないエラーハンドリング分岐
- 「将来のため」と書かれた未使用のパラメータ・フィールド・戻り値

## 証拠要件

finding を出す前に、必ず実地で確認する。確認していない推測を報告しない。

| 主張 | 確認方法 |
|---|---|
| 呼び出し元が無い | `rg` でシンボル名を全文検索。動的参照（文字列経由、リフレクション、設定ファイル）も探す |
| 既存ヘルパで代替できる | 代替先のシグネチャと挙動を読み、差分が無いことを確認する |
| 依存が不要 | その依存の import 箇所を列挙し、標準ライブラリ側の代替 API を特定する |
| 抽象化の実装が 1 つ | 実装クラスを全文検索し、テスト用モックを除いた数を数える |

確認しきれない場合は断定せず `unknown` として、何が確認できなかったかを書く。
「たぶん使われていない」は報告しない。

## 報告形式

finding ごとに次を書く。

```
対象:     <file>:<line>
主張:     何が不要か
証拠:     どう確認したか（検索コマンドとその結果）
削除案:   削除するか、何に置き換えるか
影響:     削減される行数、外れる依存
```

末尾に、基点コミットと、削除判定で**却下した候補**を数行で添える。
却下したものを書かないと、次のレビューで同じ候補が再浮上する。

すべての候補を判定し終えたら止める。新しい観点を探し続けない。

## 境界

- **read-only**。コードを書き換えない。修正はユーザーが判断してから別途行う
- 正しさ・セキュリティ・性能・アクセシビリティの指摘はしない。それらは通常のレビューと `security-reviewer` の担当
- security reviewer、TDD、アーキテクチャ分析のエージェントにこの基準を混ぜない。専門レビューの出力を縮めてしまう
- ユーザーが明示した要件、リポジトリの方針、テスト、エラー処理は削除候補にしない
- 行数の削減量は結果であって目的ではない。「短いこと」ではなく「不要な複雑さが無いこと」を評価する
